2026-09-22 - CLI summarize: reconnects on a dropped connection instead of exiting (2675955)
The previous timeout fix only covered AI-provider timeouts inside a single message. It turns out bun run cli summarize could still crash outright with an unhandled "The socket connection was closed unexpectedly" error -- the whole batch rides one long-lived HTTP connection to the local server, and if that connection itself drops (network hiccup, or just the run taking a long time), the error escaped everything and killed the CLI process.
It now catches that case, logs "Connection to the server was lost ... Reconnecting and resuming ...", and retries: accounts that already finished (their account-done arrived) aren't asked for again, and since the summarize endpoint itself skips already-summarized messages unless --force, a resumed account picks up close to where it stopped. It gives up after 20 drops in a row. A real error from the server (a bad request, no summarize skill, ...) is never retried -- only a broken connection is. At the end, if any reconnects happened, it prints the true grand total across the whole run.
New exported runSummarizeWithReconnect (src/cli/index.ts), covered by 5 focused unit tests (no drop, a drop mid-run with correct account filtering and totals, a real server error not retried, giving up after the retry limit, a drop before anything is known yet). Backend 495 pass, frontend 364 pass, build OK.

2026-09-22 - CLI summarize: timeouts no longer stop the batch (0782042)
bun run cli summarize had a "stop after 5 failures in a row" safety net meant for things like a wrong API key, but it also counted AI timeouts (the provider took too long to answer) toward that count -- so a slow or overloaded server could abort an account partway through. Timeouts are now logged and skipped like any other failure, but never count toward the circuit breaker, however many happen in a row; only five non-timeout failures in a row (wrong key, request rejected outright) still stop an account. The CLI marks a timed-out message as "TIMED OUT ... logged, moving on" instead of "FAILED".
Under the hood: services/ai.ts now throws a distinct AiTimeoutError for a request that timed out, and the batch (also used by the Summarize button's endpoint) only counts other errors toward the stop condition. Backend 490 pass, frontend 364 pass, build OK.

2026-09-21 - Conversations, "replied", and the earlier messages of a conversation (453ba7b)
-----------------------------------------------------------------------------------------
How messages are connected: by what they say about each other - Message-ID, In-Reply-To, References - over all of the user's accounts. Nothing new is
stored (no thread column, no backfill of old mail, nothing to keep in step as mail arrives). New index emails(in_reply_to); with the existing
emails(message_id) it answers, for a page of a list, in two lookups: has the user answered this message (a message from one of their own addresses has it
as In-Reply-To - drafts and copies in other folders don't count) and how many messages are directly related to it. The whole conversation of one message is
walked when it is opened: to what it refers (In-Reply-To and References, so a missing message doesn't cut the chain) and to what answers it, level by level,
at most 60 messages, copies counted once, drafts left out. 100 000 messages: a page of 100 in a few milliseconds.
What the user sees (subtle on purpose):
- In the lists (folder, combined Inbox/Sent/Imbox, search): two small quiet icons at the end of the subject line - a speech-bubble pair for "part of a
  conversation" (tooltip: how many related messages) and a reply arrow for "you replied". Messages that are neither show nothing.
- In the reading pane, only for a message that has relatives: one muted line under the header, "Conversation - 3 messages (this is 2 of 3)", that unfolds into the
  messages before and after it, oldest first: who (yours are "You"), when, how it starts, an unread dot; the current one is marked. A click opens that message in
  the reading pane wherever it lives (Inbox, Sent, another account) - like a search result it becomes the open message without moving the list, the filter or the
  sidebar. So the earlier messages of a conversation are one click away.
- When the message was answered: a small reply icon beside its subject, and "See your reply" in the conversation line, open the answer.
API: GET /api/accounts/:email/emails/:id/conversation -> { messages: [{ id, accountEmail, folder, subject, from, date, isRead, own, snippet, current }], repliedBy };
list rows get conversation: { replied, related } only when there is something to say (so nothing changes for messages without relatives).
Not covered, on purpose: no matching by subject (a "Re:" without headers stays alone rather than joining strangers); a reply that has only References and no
In-Reply-To finds its parent but is not found from it; the IMAP \Answered flag isn't used (an answer is recognised by the reply being in the mailbox); the icons
don't refresh the moment a reply is sent, only with the next list refresh.
Tests: the model (chains from any message, References with gaps, out-of-order arrival, across accounts, repliedBy, copies, drafts, the 60 cap and loops, other
users, the indexes and the timing on 100 000 rows), the HTTP routes, and the UI (list icons, the bar folded/unfolded, opening another message, See your reply,
the header icon, nothing without a conversation). Not looked at in a browser.


2026-09-21 - Imbox: learning from the user, domain knowledge, calendar invitations, unread count (4367eec)
-------------------------------------------------------------------------------------------------------
Learning from the user
- A quiet mark beside the subject in the message header (only while the imbox is on; lit while the message is in the Imbox, disabled on a
  disabled account): one click marks the message important or not important. That is the strongest signal: the verdict is stored as set by hand
  (emails.imbox_manual - no classification, not even "imbox classify --force", overwrites it) and it is ONE VOTE about the sender's address
  (table imbox_feedback: counts per sender and the latest opinion). What arrives later from that address follows the latest opinion, whatever
  the score - a newsletter marked important stays in, a friend's chain letter marked not important stays out; only Junk and one-time codes still
  rule a message out. A message carries one vote (marking it the other way replaces it; taking the mark back removes it and hands the message
  back to the classifier; a sender nobody has an opinion on any more is forgotten). The toast says what it will do for the sender.
- Reading habits, from the same pass over the mailbox as before: starred earlier mail from the address (+2, +3 from three), usually read
  (+1.5) / hardly ever read (-2), moved to Trash (-2.5). The message being classified is never its own history.
- Domain knowledge: mail from another address at the domain of one of your accounts is a colleague (+2; free-mail domains don't count, mailing
  lists don't); a sender whose mails all have the same subject shape (numbers, quoted parts, codes ignored) is a machine (-2.5).
Calendar invitations
- A .ics / text/calendar file is read (METHOD:REQUEST +3.5, CANCEL +3, REPLY or unreadable +2) unless the mail is mass mail; it also lifts the
  no-reply / platform / notification penalties, so an invitation through a calendar system's address (Google Calendar) still counts. Event
  announcements in newsletters count +0.5.
Unread count
- GET /api/unified/imbox/unread, and a badge on the Imbox entry; reading an important message lowers it at once, marking, moving, deleting and
  syncing re-read it.
Also: imbox explain shows "decided by your mark on this sender" and "set by hand"; the explain route returns manual and decidedBy.
Tests: every new signal alone; marks and votes (replace, take back, latest opinion, per sender/user, protected from --force); the mailbox statistics
(read/starred/Trash, the message itself excluded, shapes, own organisation); invitations read from real .ics files (and missing ones); the
unread count; the HTTP flow; the header mark (states, request, toast, disabled account, badge). Not run on a real mailbox: weights are still
tuned on fixtures - use "imbox explain" on your own mail and mark what is wrong; the marks are exactly the data that improves it.
Not built: learning across senders (a mark teaches one exact address, not "everything from that domain"), reclassifying that sender's OLD mail
when you mark one message (only future mail follows; old mail keeps its verdict unless you run "imbox classify --force"), and deletions that
bypass Trash (a permanent delete leaves nothing to count).

2026-09-21 - Imbox: a local classifier for important mail (4f9ef9d)
-------------------------------------------------------------------
Every message can now be classified as important or not: emails.imbox (1 / 0 / NULL = not yet), a partial index for the list, and
- a CLASSIFIER that runs entirely on this computer (no AI service, no new module needed): services/imbox/classifier.ts, pure, adds up

2026-09-20 - New folders, created on the IMAP server (6d306dd)
--------------------------------------------------------------
An account's menu (the three dots) has "New folder...": a name and, optionally, a folder to put it in ("Inside", default
top level). The folder is created on the mail server itself and subscribed to, so every other mail client sees it too;
the sidebar then shows it (subfolders are indented by depth).
- POST /api/accounts/:email/folders { name, parent? } -> 201 { path, folders }. The server's list afterwards is stored
  (the folder cache) and returned with the counts. The path is parent + the server's delimiter + name.
- Names are checked before anything is sent: 1-100 characters, no delimiter, "*", "%" or control characters, not "."
  or ".."; an existing folder (any case) is 409, an unknown parent 404. Servers that keep everything under "INBOX."
  (Dovecot's namespace prefix) get "top-level" folders there too, as they refuse names outside it.
- Read-only accounts and disabled accounts can't create folders (409, and the menu entry isn't shown): it would be a
  change on the server, which read-only exists to prevent, and a folder that only exists locally would be a lie.
  A server that refuses or can't be reached is a 502 with its reason, shown in the dialog.

2026-09-20 - Several passkeys per profile (6b5030c)
-------------------------------------------------
The passkey unlock of the saved password (browser-local, WebAuthn PRF) now supports more than one passkey per
profile on a device - Touch ID plus a security key as a backup, for instance.
- Every passkey holds its own copy of the same password, encrypted with a key only that passkey can produce
  (its own salt and IV), so they are independent: any one signs you in, and removing one leaves the others
  working. The sign-in prompt offers all of the profile's passkeys and the browser lets you use whichever
  authenticator is at hand (with several, the PRF salts are passed per credential, evalByCredential).
- Settings > Credentials lists the passkeys ("Passkey 1 . added <date>", each with Remove) and has "Add another
  passkey": it unlocks the stored password with an existing passkey (one prompt), creates the new passkey and
  derives its key (two more) - no retyping of the password. The passkeys already registered are excluded, so the
  same authenticator can't be added twice (explained in the UI); a failed or cancelled add changes nothing.
  Removing the last one removes the feature for the profile; a password change still removes everything.
- Storage format v2 (a list of entries); the single-passkey format written before is still read, unlocked and
  can be extended.
- What this does not do (by decision): share a passkey's vault between browsers/devices. Each browser keeps its
  own, so a new device sets it up once at its next password sign-in. Sharing would mean storing the encrypted
  copy on the server; not done.
- Tests: the vault with a fake that models separate authenticators (adding, either one opening it, unplugged
  devices, duplicates, cancels, removal, the old format) and the Settings UI, including signing in with only the
  second passkey at hand. Still not tried with real hardware.

2026-09-19 - Passkey unlock of the saved password (bd48f3f)
------------------------------------------------------------
Verdict first: the idea is sound only when the encryption key comes out of the authenticator. "Ask for a
passkey, then decrypt with a key that is stored next to the data" would be security theatre, so that is
deliberately NOT built. What is built uses the WebAuthn PRF extension (FIDO2 hmac-secret): the authenticator
derives a secret from a random salt only after user verification (fingerprint/face/PIN/touch), the page turns
it into an AES-GCM key, and localStorage holds only ciphertext. Without the authenticator the blob is useless;
XSS can at most trigger a prompt you would have to pass. Where PRF isn't supported nothing is stored.
- Sign-in screen: for a profile that needs a password and a browser with passkeys, a checkbox "Remember on
  this device, unlocked by a passkey / Touch ID / security key" (two prompts: create the passkey, use it once
  to derive the key; nothing stored if that fails or the authenticator has no PRF - the user is told, and is
  signed in regardless). Next time the profile shows "Unlock with passkey": one touch, then it signs in with
  the decrypted password. Cancelling shows why and leaves the password form; a saved password that the server
  rejects (changed elsewhere) is dropped with an explanation.
- Settings > Credentials shows when it is set up on this device and has a Remove button; changing the password
  removes it (it would be stale) and the toast says so.
- The blob is bound to the profile name (AES-GCM associated data), uses a fresh salt/IV on every save and is
  per profile. Client-side only: no server change.
- Tests: the vault with a fake PRF authenticator (round trip, no plaintext, fresh salts, cancel, no-PRF refusal,
  tampering, moved blob, wiped passkey) and the UI flows. Real authenticators could not be tried here - worth a
  manual check with Touch ID / a YubiKey (PRF support varies by browser and authenticator).
- Not done: enabling it later from Settings (it needs the password, so it is offered at sign-in), and
  syncing it across devices (it is per device by design).

2026-09-19 - Gmail folder list that never answered (7dd7bfa)
-----------------------------------------------------------
Diagnosis (done against the real Gmail account, with a separate diagnostic server on another port; only
read-only IMAP calls): curl showed "Empty reply from server" after ~10 s. Two causes together:
1. The live IMAP listing was extremely slow - connect+login 30 s, LIST 10 s, LOGOUT 10 s (~50 s in total) -
   and a moment later Gmail closed the connection right after the TLS handshake with "Account exceeded command
   or bandwidth limits." So Gmail is throttling the account (other clients - Apple Mail, a ruby process - were
   connected too, and our sync of all folders downloads whole mailboxes at once, 44,000 messages in the
   Inbox). Nothing in the app can lift that; it usually clears after some hours without heavy use.
2. The app hid it: Bun.serve's default idleTimeout is 10 s and silently drops a request that hasn't
   answered by then, so instead of any error the browser got an empty reply.
Fixes:
- Bun.serve idleTimeout: 120 (restart `bun run dev` - hot reload does not re-apply server options).
- The folder list is now remembered per account (accounts.folders_cache): a plain request is answered from
  it instantly with fresh counts, and never touches IMAP; `?live=1` reads IMAP. The web client shows the
  cached tree first and refreshes it live in the background (keeping what is shown if that fails); refreshing
  counts after a sync no longer opens an IMAP connection at all. Without a cache the first request goes
  live. Concurrent live listings of an account share one connection.
- Failures are errors with the reason instead of silence: "Couldn't read the folders of ... from
  imap.gmail.com: Unexpected close (code=ClosedAfterConnectTLS, server said: "Account exceeded command or
  bandwidth limits.") - the mail server is throttling this account; it usually lifts after some hours". That is
  also what the sidebar shows now. IMAP connections time out after 30 s (connect) / 20 s (greeting), and the
  client gets an "error" listener so a dropped connection can't become an uncaught exception.
- Tests: the folder route with cache/no cache/live failures, the error text, and the tree showing cached
  folders first, keeping them when the live read fails, and not re-reading IMAP for count refreshes.
Not fixed here (worth doing next): a sync downloads a whole folder in one request and stores nothing until
it is complete, so an interrupted or restarted sync (dev hot reload!) starts over from zero - repeated
full downloads are exactly what triggers Gmail's limits, and the dev server had grown to ~2.6 GB. Downloading
and storing in batches (say 200 messages at a time) would fix both.

2026-09-19 - Better recipient autocomplete (8c6966f)
---------------------------------------------------

2026-09-19 - Change password, tabbed Settings (a3f2792)
-----------------------------------------------------
- The Settings dialog now has three tabs: Inboxes (sync interval, folders in the combined Inbox),
  Notifications (browser notification, toast, sound) and Credentials (change password). Inboxes and
  Notifications share one Save button (edits on both tabs are saved together); Credentials has its
  own "Change password" button.
- Changing the password needs the current one, a new one and its confirmation (the passwordless
  default profile leaves "current" empty and can thereby set a first password).
- The important part - the encryption: the saved IMAP/SMTP passwords of your mail accounts are
  encrypted with a key derived from your login password and a salt. So a password change decrypts
  every account secret with the old key and re-encrypts it with the key for the new password and a
  fresh salt, in the same transaction as the new password hash: it is all-or-nothing. If some
  account's secrets can't be decrypted it refuses with a message naming that account (re-enter its
  passwords in Account settings first) and changes nothing.
- Sessions: the key lives in server memory per session. The session you change the password in is
  given the new key and keeps working; your other sessions/browsers are signed out (their keys would
  be stale), and the toast says how many.
- New endpoint POST /api/auth/change-password. The existing PATCH /api/users/:id (password) only
  swapped the hash and would have left every saved account password undecryptable; it now needs
  currentPassword as well and goes through the same re-encryption.
- Tests: model (re-encryption, wrong password, all-or-nothing, default user), integration (full HTTP
  flow incl. other session signed out and secrets readable with the new key/salt), and the tabs and
  form in the frontend. The old model test for updateUserPassword was replaced.
