2026-09-19 - Attachment download fix for non-ASCII filenames (afe36d5)
----------------------------------------------------------------------
Downloading an attachment whose filename contains non-ASCII characters (e.g. "Flyer Chor Jubiläum Herder NEU.pdf")
failed with a 500 because HTTP header values must be ASCII and Bun rejected the Content-Disposition header. The
download route now sends an ASCII fallback filename (non-ASCII characters replaced by "_") plus a percent-encoded
UTF-8 "filename*" parameter, so browsers keep the real name. Verified only with a standalone Response, not by
downloading a file in the running app.

2026-09-19 - Passkey unlock of the saved password (bd48f3f)
------------------------------------------------------------
Verdict first: the idea is sound only when the encryption key comes out of the authenticator. "Ask for a
passkey, then decrypt with a key that is stored next to the data" would be security theatre, so that is
deliberately NOT built. What is built uses the WebAuthn PRF extension (FIDO2 hmac-secret): the authenticator
derives a secret from a random salt only after user verification (fingerprint/face/PIN/touch), the page turns
it into an AES-GCM key, and localStorage holds only ciphertext. Without the authenticator the blob is useless;
XSS can at most trigger a prompt you would have to pass. Where PRF isn't supported nothing is stored.
- Sign-in screen: for a profile that needs a password and a browser with passkeys, a checkbox "Remember on
  this device, unlocked by a passkey / Touch ID / security key" (two prompts: create the passkey, use it once
  to derive the key; nothing stored if that fails or the authenticator has no PRF - the user is told, and is
  signed in regardless). Next time the profile shows "Unlock with passkey": one touch, then it signs in with
  the decrypted password. Cancelling shows why and leaves the password form; a saved password that the server
  rejects (changed elsewhere) is dropped with an explanation.
- Settings > Credentials shows when it is set up on this device and has a Remove button; changing the password
  removes it (it would be stale) and the toast says so.
- The blob is bound to the profile name (AES-GCM associated data), uses a fresh salt/IV on every save and is
  per profile. Client-side only: no server change.
- Tests: the vault with a fake PRF authenticator (round trip, no plaintext, fresh salts, cancel, no-PRF refusal,
  tampering, moved blob, wiped passkey) and the UI flows. Real authenticators could not be tried here - worth a
  manual check with Touch ID / a YubiKey (PRF support varies by browser and authenticator).
- Not done: enabling it later from Settings (it needs the password, so it is offered at sign-in), and
  syncing it across devices (it is per device by design).

2026-09-19 - Gmail folder list that never answered (7dd7bfa)
-----------------------------------------------------------
Diagnosis (done against the real Gmail account, with a separate diagnostic server on another port; only
read-only IMAP calls): curl showed "Empty reply from server" after ~10 s. Two causes together:
1. The live IMAP listing was extremely slow - connect+login 30 s, LIST 10 s, LOGOUT 10 s (~50 s in total) -
   and a moment later Gmail closed the connection right after the TLS handshake with "Account exceeded command
   or bandwidth limits." So Gmail is throttling the account (other clients - Apple Mail, a ruby process - were
   connected too, and our sync of all folders downloads whole mailboxes at once, 44,000 messages in the
   Inbox). Nothing in the app can lift that; it usually clears after some hours without heavy use.
2. The app hid it: Bun.serve's default idleTimeout is 10 s and silently drops a request that hasn't
   answered by then, so instead of any error the browser got an empty reply.
Fixes:
- Bun.serve idleTimeout: 120 (restart `bun run dev` - hot reload does not re-apply server options).
- The folder list is now remembered per account (accounts.folders_cache): a plain request is answered from
  it instantly with fresh counts, and never touches IMAP; `?live=1` reads IMAP. The web client shows the
  cached tree first and refreshes it live in the background (keeping what is shown if that fails); refreshing
  counts after a sync no longer opens an IMAP connection at all. Without a cache the first request goes
  live. Concurrent live listings of an account share one connection.
- Failures are errors with the reason instead of silence: "Couldn't read the folders of ... from
  imap.gmail.com: Unexpected close (code=ClosedAfterConnectTLS, server said: "Account exceeded command or
  bandwidth limits.") - the mail server is throttling this account; it usually lifts after some hours". That is
  also what the sidebar shows now. IMAP connections time out after 30 s (connect) / 20 s (greeting), and the
  client gets an "error" listener so a dropped connection can't become an uncaught exception.
- Tests: the folder route with cache/no cache/live failures, the error text, and the tree showing cached
  folders first, keeping them when the live read fails, and not re-reading IMAP for count refreshes.
Not fixed here (worth doing next): a sync downloads a whole folder in one request and stores nothing until
it is complete, so an interrupted or restarted sync (dev hot reload!) starts over from zero - repeated
full downloads are exactly what triggers Gmail's limits, and the dev server had grown to ~2.6 GB. Downloading
and storing in batches (say 200 messages at a time) would fix both.


2026-09-19 - Disabled mail accounts (047798c)
----------------------------------------------
Account settings > Safety has a new "Disabled" switch (new accounts.disabled column, migrated; also
`disabled` in the account PATCH body). A disabled account is frozen:
- Not synced: the sync route answers 409, the sidebar shows no Sync button (the account is struck through with
  a "Disabled" mark), the automatic sync skips it, and a sync that is already running stops before storing
  anything more (the job fails with "The account was disabled during the sync").
- No connections at all: its folder list is built from the stored mail alone (no IMAP), the capability check
  is refused, and it can't send.
- Automatically read-only: the Read-only switch shows as on and can't be changed while disabled; nothing is
  pushed to its IMAP server.
- Its stored mail is immutable, not just "local-only": every route that would change it answers 409 with
  "Account ... is disabled" - creating/editing/sending drafts, flags and read state, moves, deletes, the bulk
  versions, attachments upload/delete, and AI summaries/translations/categories (they are stored on the
  message). The web client greys out Reply, Reply all, Forward, Mark read, Move, Delete, Edit draft, New and
  Translate for such messages (tooltip: "This account is disabled"), refuses stars/bulk actions up front with
  a message instead of a request, and doesn't mark messages read when you open them.
- Still possible: reading (lists, messages, attachments, search, the combined lists, an existing summary),
  re-enabling, editing the settings, and removing the account.
- Decision: removing a disabled account is allowed (it is an explicit administrative act, not an edit of the
  mail), and AI results count as changes, so they are refused too.
- Tests: the whole HTTP surface (15 refused mutations, the DB unchanged, no sync job, folders without a
  connection, re-enable), a sync stopping when the account is disabled mid-run, and the UI (switch, row,
  toolbar, star, no mark-as-read, automatic sync).

2026-09-19 - AI: summarize, categorize, translate, refine (acd1c9d)
-----------------------------------------------------------------
Settings has a new "AI" tab (between Notifications and Credentials).
- AI providers (table ai_apis): each has a vendor (Anthropic, OpenAI, Google Gemini, Ollama), a model
  (e.g. claude-opus-5), an API key and optionally an address (for Ollama or OpenAI-compatible services). Every
  user has many. The key is stored encrypted with the user's key, exactly like the mail account passwords,
  and is never sent back to the browser (only "key saved"). Changing the login password re-encrypts the AI
  keys along with the account passwords (and refuses, naming the provider, if one can't be decrypted). A
  "Test" button checks that a provider answers.
- Skills (table ai_skills): a category (Summarize, Categorize (taxonomy), Translate, Spelling + Grammar,
  Phrase), a name, a prompt (agent instruction) and exactly one provider. Choosing a category suggests a
  prompt, taken from src/ai/skillDefaults.json - the single place to refine the suggestions over time
  (the translate prompt has a {{language}} placeholder). The prompt follows category changes until you
  edit it by hand, and "Use suggested prompt" restores it. With several skills of a category the oldest is
  used. Deleting a provider deletes its skills (the dialog says how many).
- New message columns: taxonomy_list (JSON array of 2-6 labels), ai_summary, translated_text and (my addition)
  translated_language, so results are stored permanently and not paid for twice. Existing databases are
  migrated.
- Reading pane: "Summarize" stores the summary and - when a Categorize skill exists - the taxonomy in the same
  go (a failing categorize step doesn't lose the summary and is reported). The summary and the labels (chips)
  show above the message. "Translate" stores a translation into the language set under "Translate into" and
  adds a "Translation" tab, which opens right away (a transient choice, not stored as the preferred view).
- Compose: a "Refine" menu with Phrase, Spelling + Grammar and Translate... (asks for the language, starting
  with your setting). It only rewrites the part you wrote - not the signature, the quoted original of a reply
  or a forwarded message - and there is an Undo. Items without a matching skill are disabled, as are the
  reading pane buttons.
- Vendors are called from the server with plain fetch: Anthropic messages, OpenAI-style chat completions
  (also for compatible services via the address), Gemini generateContent, Ollama chat; 90 s timeout, texts
  cut at 60,000 characters, vendor errors passed on as a 502 with their message.
- Privacy: the text of the message or draft is sent to the provider you configured, and only when you press
  one of these buttons (the Settings tab says so).
- New endpoints under /api/ai/... and .../emails/:id/ai/{summarize,categorize,translate}; user setting
  aiTargetLanguage. Tests: models, vendor request shapes, prompt/answer helpers, the whole HTTP flow with a
  stubbed AI (incl. isolation between users and the password change), the Settings tab, both buttons and
  Refine. The suggested prompts and the vendor request shapes are worth checking against the vendors' current
  docs - I could not call any real API here.
- Not done: searching or filtering by taxonomy label, showing labels in the message list, choosing between
  several skills of one category, and streaming answers.

2026-09-19 - Better recipient autocomplete (8c6966f)
---------------------------------------------------
1. Punctuation no longer matters. A contact stored as 'First Lastname' <flastname@example.com> wasn't
   found by typing First because the quotes were part of the first word. Names are now compared as
   plain words (case and any punctuation ignored, letters/digits of any script, so umlauts work):
   First, 'First, last first and first-last all find it. Every typed word has to be the start of some
   word in the name (irst finds nothing), or the address has to start with what you typed (that part
   keeps its punctuation: first.l). Quotes around names are also stripped when a contact is stored,
   and existing contacts are tidied once at startup (so old data is fixed too, and the suggestion
   shows First Lastname without quotes).
2. Contacts from other accounts: instead of a button, they are appended automatically, under a
   "From your other accounts" heading, after the current account's own matches (up to 5, ranked the
   same way; an address known to several accounts shows once with its counts added up; never an
   address the current account already has). This account's people always stay first, so the
   "only this account" feel is kept, but you never have to click anything to reach the rest, and the
   arrow keys walk through both groups. I chose this over a button because a button hides the
   contacts exactly when you need them, at the cost of a slightly longer list. The API only does it
   with scope=all (the recipient fields always ask for it); otherwise it is still this account only.
- Tests: quoted/punctuated/umlaut names, word order, address prefixes, the startup repair; other-account
  ranking, caps, dedupe and isolation between users; the heading and keyboard/mouse selection in the UI.

  default profile leaves "current" empty and can thereby set a first password).
- The important part - the encryption: the saved IMAP/SMTP passwords of your mail accounts are
  encrypted with a key derived from your login password and a salt. So a password change decrypts
  every account secret with the old key and re-encrypts it with the key for the new password and a
  fresh salt, in the same transaction as the new password hash: it is all-or-nothing. If some
  account's secrets can't be decrypted it refuses with a message naming that account (re-enter its
  passwords in Account settings first) and changes nothing.
- Sessions: the key lives in server memory per session. The session you change the password in is
  given the new key and keeps working; your other sessions/browsers are signed out (their keys would
  be stale), and the toast says how many.
- New endpoint POST /api/auth/change-password. The existing PATCH /api/users/:id (password) only
  swapped the hash and would have left every saved account password undecryptable; it now needs
  currentPassword as well and goes through the same re-encryption.
- Tests: model (re-encryption, wrong password, all-or-nothing, default user), integration (full HTTP
  flow incl. other session signed out and secrets readable with the new key/salt), and the tabs and
  form in the frontend. The old model test for updateUserPassword was replaced.
